# request-triage

Один проход: сообщение → контекст → recall-first → read-only диагностика → ответ → dated-документ.

База знаний — `{{KB_ROOT}}` (дальше `$DOCS`; он же Obsidian vault), её правила — `$DOCS/AGENTS.md`,
поиск по ней — MCP-инструмент `kb_search` или `python3 {{HARNESS_HOME}}/tools/kb.py search`.

## 1. Контекст

- Ссылка на пост `{{CHAT_URL}}/<team>/pl/<id>` (Mattermost-стиль; или постоянная ссылка вашего чата): раскрой ссылку
  в пост (`mm_resolve_permalink`), затем прочитай тред (`mm_get_thread`). Ключ трекера обычно в ответе бота дежурства
  («Создан тикет: {{TICKET_EXAMPLE}}»). Пост в каналах `{{ALERT_CHANNELS}}` или в формате Alertmanager (`Alert:`,
  `Severity:`, `Firing`) — алерт, остальное — обращение.
- Ключ трекера из треда или от пользователя: получи задачу (`jira_get_issue`).
- Алерт: проверь, горит ли он сейчас (`am_active_alerts`), затем агрегаты метрик и логов в узком окне — запрос к
  метрикам (`query`/`query_range` MCP VictoriaMetrics или `vm_query`/`vm_query_range` из `{{MCP_HUB}}`) и к логам
  (`vl_query`).

Готово, когда известны источник, тип (обращение или алерт), ключ трекера или подтверждённое его отсутствие, сервис,
среда и время.

## 2. Recall-first

Поиск по базе знаний (`kb_search` из `{{MCP_HUB}}`) с запросом «<сервис> <симптом> <alertname> <тикет>» (без MCP —
`python3 {{HARNESS_HOME}}/tools/kb.py search "…"`). По сервису или тикету сначала открой его хаб
(`$DOCS/services/<Name>.md`, `$DOCS/tickets/<KEY>.md`). Читай только выданные разделы: `sed -n 'A,Bp' <path>`.

Готово, когда по каждому найденному документу принято решение: тот же случай (тот же сервис и симптом) — обновляешь
его; смежный — сошлёшься на него в разделе «Похожие обращения»; совпадений нет — случай новый.

## 3. Диагностика (read-only)

По симптому, только чтение: репозиторий кода (`gitlab_get_file`, `gitlab_get_mr`, `gitlab_search`), GitOps-контроллер
(`argocd_app_get`, `argocd_app_diff`, `argocd_app_history`), Helm (`helm_template_summary`, `helm_values_schema`),
Terraform/Terragrunt (`*_validate`, `*_plan_summary`), хранилище секретов (`vault_status`, `vault_kv_metadata_get` —
только метаданные), метрики и логи, дашборды. Версия автора обращения — гипотеза, её проверяют как любую другую.

Широкий поиск — по нескольким репозиториям, логам за большое окно или с проверкой противоречий между
источниками — либо любой поиск, когда контекст уже заполнен больше чем наполовину, в Claude поручи субагенту
`kb-scout` с точным вопросом и списком того, что вернуть. В Codex ищи сам, а `kb_scout` зови только при
заполнении контекста больше чем наполовину: на замерах он был заметно дороже по токенам и менее точен. Точечную
проверку (один файл, один запрос, одна метрика) делай сам: так точнее и быстрее.

Готово, когда причина подтверждена доказательством (файл:строка, коммит, вывод команды, метрика) или явно помечена
неизвестной вместе со следующей безопасной проверкой. Это Sev1/Sev2 с простоем — предложи перейти на `postmortem`.

## 4. Ответ в чат (5–8 строк)

Суть в одну строку; причина с доказательством; решение как предложение (для изменения — blast radius, rollback,
команда проверки); похожие прошлые случаи со ссылками; путь документа из шага 5.

## 5. Документ

1. Шаблон: [`templates/duty_request.md`](templates/duty_request.md) для обращения (папка `$DOCS/duty/`),
   [`templates/alert_rca.md`](templates/alert_rca.md) для алерта (`$DOCS/alerts/`). Имя — `<KEY>-<slug>-<YYYY-MM-DD>.md`,
   без тикета — `<slug>-<YYYY-MM-DD>.md`. Тот же случай из шага 2 — дополняешь существующий документ.
2. Frontmatter заполнен целиком: `summary` — симптом → причина → решение в одну-две фразы, `services` — канонические
   имена из `$DOCS/navigation/glossary.md`. При нехватке данных документ всё равно пишется: в нём фиксируются
   ограничения, непроверенные гипотезы и следующие проверки.
3. `python3 {{HARNESS_HOME}}/tools/kb.py lint` сообщает `OK`, а `kb.py search "<KEY>"` выдаёт документ первым.
4. Коммит в `main` основной копии `$DOCS` (по `$DOCS/AGENTS.md`): `git -C $DOCS add <файл>`, затем
   `git -C $DOCS commit -m "<KEY> document <что>"`. Тикета нет — спроси пользователя, под каким ключом коммитить.

Документ в `$DOCS` и есть запись находки; через `obsidian_append_finding` (в `$DOCS/findings/`) уходит только
побочная находка, не относящаяся к этому обращению.

Готово, когда документ закоммичен, lint чистый и поиск по ключу его находит.

## 6. Трекер

Для тикетов проектов `{{TICKET_PREFIXES}}` предложи пользователю комментарий в задаче (`jira_add_comment`) с причиной,
решением и путём документа; комментарий пишется только после его согласия.

Полный проход на примере обращения: [`references/worked-example.md`](references/worked-example.md).
