## Remote state is read-only

- Cloud, Kubernetes, secret managers, Argo CD, Terraform/Terragrunt, Helm and CI are read-only. Work through
  dry-run, diff, validate, lint, plan, template, get, list, describe, status and read.
- A remote write needs the user's explicit approval for that one concrete action; approval does not
  carry over to related or later actions, and a permissive local sandbox is not approval. Before
  asking, state the expected state change, blast radius, rollback path and verification command.
- Hard guardrail, never run or suggest unattended: `terraform|terragrunt apply|destroy`,
  `kubectl delete|patch|scale|rollout restart`, `argocd app sync|rollback|delete`,
  `helm upgrade|uninstall`, `vault write|delete`, cloud CLI `delete|update`, CI pipeline mutations.
  When unsure whether a command writes, treat it as a write.
- GitOps: change Git and let the controller reconcile. Direct cluster mutation only as break-glass the
  user explicitly asks for.
- Terraform/Terragrunt: read module/provider versions and the backend/remote state config before
  proposing a change.
- Secrets stay out of prompts, patches, skills, logs, artifacts and answers: tokens, private keys,
  kubeconfigs, secret-manager values, OAuth/JWT, customer data. External documentation searches carry only
  generic technology/version questions, never internal names or data.

## Tooling

- `{{MCP_HUB}}` MCP is the integration surface (tracker, wiki, chat, alerts, metrics, logs, dashboards, git
  hosting, knowledge base); reach for it before curl or guessed internal URLs. Prefer tools that aggregate
  (patterns for logs, min/max/percentiles for metrics) and work from the summary, not raw points.
- Documentation lives in one place, `{{KB_ROOT}}` (git repo and Obsidian vault). Recall first: `kb_search`
  (shell fallback `python3 {{HARNESS_HOME}}/tools/kb.py search "<service> <symptom> <ticket>"`) before an
  expensive log/metric dive; read only the returned line ranges. A finished investigation becomes a dated doc
  there (its `AGENTS.md` says how); a short side finding goes to `findings/`.
- Writes to tracker, wiki, git hosting and chat go only through tools the user has allowed. A rejected write is
  reported as rejected; a comment or post counts as done only when the tool returned success.

## Tracker and Git

For any change to files in a work Git repo (not `{{KB_ROOT}}`, see its own rules):

1. Establish one tracker key (`{{TICKET_EXAMPLE}}`) before editing or branching. Take candidates from the
   request, current branch and repo context; verify that the issue exists, or search for it.
2. No verified key: create exactly one issue in project `{{TRACKER_PROJECT}}`, type `{{TRACKER_ISSUE_TYPE}}`,
   assignee `{{TRACKER_ASSIGNEE}}` (another type or person only if the user asks). Summary from the requested
   change, context in the description. This is standing authorization for this one tracker write; other tracker
   writes need normal approval. If creation fails, stop and report: no edits, no untracked branch.
3. Branch name is exactly the key. Reuse an existing branch of that name when the tree is clean, or stay on the
   current branch if it already carries the key. A dirty tree or another non-default branch with unrelated work:
   ask before switching. Create worktrees with `--no-track` so editor sync never pushes into the default branch.
4. Commit the finished, verified change on the task branch yourself; push and merge requests only when the user
   asks. Commit subject: `<KEY> <imperative summary>`. Tracker comments, when asked for, use the same format.
5. Before handing off, confirm `git branch --show-current` and, if you committed, `git log -1 --pretty=%s` both
   carry the key.

## Long tasks

- All chats start from `{{WORK_DIR}}`; the task journal is bound to the chat, not the folder. A message that
  starts with a key (`{{TICKET_EXAMPLE}} продолжаем`) binds the chat to that task's journal.

  (`{{KB_ROOT}}/tasks/<KEY>-<slug>/handoff.md`); hooks nudge at the configured context thresholds and restore the
  journal after compaction.
- Broad searches and log digs go to a read-only subagent that returns a short summary (Claude: `kb-scout`;
  Codex: `kb_scout`).

## Context economy

- Scope queries by repo, service, namespace and time window; aim for 2,000-6,000 output tokens per call and
  treat truncated output as incomplete.
- Keep large evidence in a local file after redaction and pass its path with a short summary.
- A handoff to another agent carries the objective, decisions, verified evidence, authorization scope, changed
  files and next checks.
