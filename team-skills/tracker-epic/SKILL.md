# Эпик с подзадачами

Скилл заводит эпик и, если пользователь их перечислил, подзадачи под ним, со связью «задача → эпик» в том виде,
который требует ваш трекер. Отвечает только за трекер; квартальную страницу в вики ведёт
[`quarterly-planning`](../quarterly-planning/SKILL.md), который вызывает этот скилл для шага с эпиком.

Файлы скилла:

* [`templates/epic.wiki`](./templates/epic.wiki) — структура описания эпика;
* [`defaults.yaml`](./defaults.yaml) — проект, типы, метки, поля эпика, поведение.

## Когда применять

* «заведи эпик про чистку техдолга»;
* «нужен эпик под миграцию X»;
* «создай эпик и нарежь подзадачи: A, B, C»;
* шаг «создать эпик» из `quarterly-planning`.

Не применять:

* для квартальной цели целиком — [`quarterly-planning`](../quarterly-planning/SKILL.md);
* для одиночной задачи — [`tracker-story`](../tracker-story/SKILL.md);
* для багов и инцидентов;
* для пары задач под уже существующий эпик — создай задачи и свяжи их с эпиком напрямую.

## Настройка под команду

В `defaults.yaml`:

* `tracker.project_key`, `default_assignee` — по умолчанию `{{TRACKER_PROJECT}}`, `{{TRACKER_ASSIGNEE}}`;
* `tracker.issue_type`, `child_issue_type` — тип эпика и тип подзадач в вашем проекте;
* `tracker.labels`, `child_labels` — постоянные метки;
* `tracker.link_mode` — как трекер связывает задачу с эпиком:
  * `epic_link` — старые инсталляции Jira Server/DC: поле Epic Link (custom field) у задачи и обязательное поле
    Epic Name у эпика;
  * `parent` — Jira Cloud и новые версии: поле `parent` у задачи;
  * `tool` — у MCP-сервера есть отдельный инструмент связи (например, `jira_set_epic`);
* `tracker.epic_name_field`, `epic_link_field` — id custom field'ов для режима `epic_link`. Как найти: открой любую
  задачу, уже связанную с эпиком, со всеми полями (например, `jira_get_issue` с `fields=*all`) и найди поле, значение
  которого — ключ эпика; поле Epic Name ищется так же на эпике. Нашёл — предложи записать в дефолты.

## Шаги

### 1. Прочитай дефолты

Контракт команды; явные слова пользователя («в другой проект») важнее.

### 2. Собери данные

Из `quarterly-planning` данные уже собраны (summary, описание, подзадачи) — переходи к шагу 3.

Иначе собери:

* summary эпика (≤120 символов, без точки);
* короткое имя эпика (1–4 слова), если трекер его требует;
* описание по [`templates/epic.wiki`](./templates/epic.wiki): цель, контекст, скоуп, вехи, метрики успеха, риски;
* подзадачи — список коротких формулировок.

Не хватает — одно компактное уточнение. Секцию «Вне скоупа» заполняй, только если пользователь что-то явно
исключил; иначе убери её.

### 3. Заполни шаблон

Wiki markup трекера: `h1.`/`h2.`, `*`/`**` для списков, `[текст|url]`, inline-код — текст в двойных фигурных
скобках, блоки — `{noformat}` или `{code:язык}`. Не markdown.

### 4. Покажи черновик и получи подтверждение

Summary, проект, тип, метки, ~10 строк описания и список подзадач, затем «создавать эпик и N подзадач?». Без
явного «да» ничего не создавай. Пропуск — только при `behavior.confirm_before_create: false` или постоянном
разрешении в конфиге пользователя. При `behavior.confirm_children_before_create: true` подтверждение подзадач
спрашивай отдельно, если пользователь не подтвердил их вместе с эпиком.

### 5. Создай эпик

Создай задачу в трекере (например, `jira_create_issue`): проект, тип эпика, summary, описание, метки (постоянные +
пользовательские + метка квартала из `quarterly-planning`), приоритет, исполнитель. В режиме `epic_link` передай
имя эпика в поле `epic_name_field` (например, через `extra_fields`); без него трекер обычно отвечает ошибкой
«Epic Name is required». Поле неизвестно — спроси пользователя или прочитай текст ошибки.

Запомни ключ и URL эпика.

### 6. Создай подзадачи

Только если подзадачи перечислены и `behavior.create_children_if_listed: true`.

Описание каждой подзадачи — четыре блока в таком порядке:

* `h1. Зачем` — 1–3 фразы о проблеме именно этой задачи, не эпика в целом. Без этого блока исполнитель не
  понимает контекста;
* `h1. Что сделать` — постановка в одну-две фразы;
* `h1. Что считаем готовым` — 2–4 проверяемых критерия;
* `h1. Контекст` — ссылка на эпик и, если есть, на страницу квартала.

Нет основания для «Зачем» — спроси, не сочиняй.

Связь с эпиком — по `tracker.link_mode`: поле `epic_link_field` при создании, поле `parent`, или отдельный вызов
инструмента связи. Поле `parent` в режиме `epic_link` не используй: там оно только для sub-task.

Если какая-то подзадача не создалась или не связалась — не молчи, перечисли в ответе, что вышло и что нет.

### 7. Ответ

3–6 строк: эпик ключом и summary ссылкой (`{{TRACKER_URL}}/browse/<KEY>`), метки, ключи подзадач одной строкой,
отдельной строкой — что не получилось. При вызове из `quarterly-planning` верни также ключи и URL эпика и подзадач
для обратных ссылок.

## Пример

Пользователь: «заведи эпик про шумные алерты, подзадачи — аудит самых частых алертов, правила подавления,
назначение владельцев алертов».

1. Уточнение одно: «как поймём, что готово?» — «меньше 5 повторяющихся алертов в неделю».
2. Описание по шаблону: цель — снизить шум в алерт-канале; метрика — повторы в неделю; риски — потерять полезный
   сигнал при подавлении.
3. Черновик показан, получено «да». Эпик создан, три подзадачи созданы с блоками «Зачем / Что сделать / Что
   считаем готовым / Контекст» и связаны с эпиком.

## Чего не делать

* Не связывать задачу с эпиком полем, которое трекер использует для другого (`parent` в режиме `epic_link`).
* Не создавать эпик в проекте, которого нет в дефолтах или в словах пользователя.
* Не писать описание в markdown.
* Не дублировать: эпик уже создан в этом разговоре — предложи обновить.
* Не вписывать секреты, токены, внутренние адреса.
* Не управлять страницами вики квартала — это зона `quarterly-planning`.
