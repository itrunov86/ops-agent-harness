# Skill: jira-planning-story

Назначение скилла — создавать в Jira задачи планового характера по единому
шаблону, чтобы любая инициатива (внедрение, миграция, исследование, ADR)
описывалась одинаково и попадала в код-ревью команды.

Шаблон лежит рядом, в [`templates/story.wiki`](./templates/story.wiki).
Дефолты (project key, тип, лейблы, ссылки) — в [`defaults.yaml`](./defaults.yaml).
**Никогда не правь шаблон или дефолты в рантайме — только через PR.**

## Когда применять

Применяй, если пользователь хочет завести в Jira задачу из категории
«нужно проработать/внедрить/исследовать». Примеры:

* «заведи стори про внедрение OpenTelemetry»
* «создай задачу про миграцию метрик в VM»
* «оформи задачу на выбор бекенда для трейсов»
* «надо описать в джире переход на новый CI»

Не применяй для:

* багов и инцидентов — для них есть другой шаблон/тип;
* мелких операционных тасок («подними виртуалку», «выдай доступ»);
* подзадач внутри уже созданного эпика, если контракта на описание там не было.

В сомнительных случаях — спроси пользователя, подходит ли этот шаблон.

## Что делать

1. **Прочитай дефолты** из `defaults.yaml` — это контракт команды. Если в нём
   `project_key: "OPS"`, используй именно его, пока пользователь явно не указал
   другое. Если в дефолтах остался `project_key: "OPS"` и пользователь не
   подтверждал, что у него такой ключ — кратко спроси («создаю в проекте OPS,
   ок?») перед вызовом tool.
2. **Собери данные у пользователя.** Если в исходном сообщении уже есть
   готовый текст с блоками «Проблематика / План / Требования» — используй его
   как есть, без отсебятины. Если чего-то не хватает, задай *одно компактное
   сообщение* с уточнениями. Не разбивай уточнения на много раундов.
3. **Проверь минимумы качества.** Если меньше `behavior.min_plan_items`
   пунктов плана или `behavior.min_requirements` требований — попроси
   дополнить. Пустые/однострочные задачи команда не принимает.
3a. **Обогати задачу темой.** Каждая задача обязана нести ровно один
   тематический лейбл вида `<jira.theme_label_prefix><тема>` — по нему команда
   собирает статистику по направлениям в JQL. Порядок:
   - Сначала подбери тему из реестра `jira.themes` в `defaults.yaml` (это
     источник правды по направлениям). Лейбл = `theme-<ключ темы>`.
   - Если ни одна тема не подходит и задача про реально новое направление —
     согласуй короткое имя темы с пользователем, затем: (1) добавь тему в
     `jira.themes` (правка `defaults.yaml` — только через PR) и (2) допиши
     строку в таблицу «Тематические метки задач» на странице
     `confluence.themes_page` (id <ID страницы тем>, space {{WIKI_SPACE}}) через
     `confluence_update_page`. Не плоди синонимы существующих тем.
   - Тему выводи из сути задачи; если из реестра подходят несколько — задай
     пользователю *один* короткий вопрос с 2–4 вариантами. Имя темы — короткий
     kebab-case без пробелов.
   - Если `behavior.require_theme_label: true` — не создавай задачу, пока
     тематический лейбл не определён.
3b. **Добавь метки спринта.** Каждая задача ОБЯЗАНА нести два лейбла спринта:
   - `current_sprint` — уже в `jira.labels` в defaults, всегда проставляется.
   - `sprint-YYYY-wWW` — вычисляй по сегодняшней дате. Алгоритм (из defaults):
     1. `days = (today − reference_start).days`  (отрицательно, если раньше якоря)
     2. `sprint_start = reference_start + floor(days / (cadence_weeks × 7)) × cadence_weeks × 7 дней`
     3. `label = "sprint-{sprint_start.year}-w{sprint_start.isoweek:02d}"`
   - Добавляй этот лейбл к финальному списку `labels` вместе с остальными.
   - Пример (сегодня 2026-06-03, reference=2026-06-08, cadence=2):
     days=−5, index=−1, sprint_start=2026-05-25 (ISO w21) → `sprint-2026-w21`
   - Пример (сегодня 2026-06-10):
     days=2, index=0, sprint_start=2026-06-08 (ISO w24) → `sprint-2026-w24`
4. **Отрендери тело.** Открой `templates/story.wiki` и подставь значения в
   плейсхолдеры. Все списки оформляй в Jira wiki markup:
   - маркированный список — строки, начинающиеся с `*` или `**` для уровней;
   - ссылки — `[label|https://...]`;
   - inline code — `{{...}}`;
   - блоки — `{noformat}...{noformat}` или `{code:language}...{code}`.
5. **Покажи превью** (если `behavior.confirm_before_create: true`):
   summary, project key, issue type, лейблы, краткий рендер тела (~10
   строк), затем явно спроси: «создавать?». Если `false` — пропусти шаг.
6. **Создай задачу** через tool `jira_create_issue`. Передавай:
   - `project = jira.project_key` из defaults (или то, что задал пользователь),
   - `issue_type = jira.issue_type`,
   - `summary` — короткая формулировка (≤120 символов, без точки в конце),
   - `description` — отрендеренное тело шаблона,
   - `labels = jira.labels` + тематический лейбл из шага 3a + то, что
     добавил пользователь,
   - `priority = jira.priority`, если задан,
   - `assignee = jira.default_assignee`, если не пусто.

   После успеха верни пользователю созданный ключ и `url`.
7. **Дополнительно (если уместно):**
   - Если в `confluence.link_bookmark` указана закладка и в секции «Связанные
     документы» её ещё нет — добавь ссылку до создания задачи. Использовать
     `confluence_get_bookmark(name)` только если нужен URL, иначе можно
     вписать заглушку и попросить пользователя подтвердить.
   - Если пользователь упомянул родительский epic (`OPS-42`) и
     `behavior.link_to_epic_if_mentioned: true` — после создания вызови
     `jira_update_issue` и проставь поле epic-link (имя поля разнится между
     инстансами; для Jira Server обычно `customfield_10008` или
     `customfield_10014`, спроси пользователя если не уверен).

## Контракт ответа пользователю

После создания задачи коротко (3–5 строк):

* `*<KEY>* — <summary>` (ссылкой);
* проект, тип, лейблы;
* что лежит в задаче (одной строкой: «5 пунктов плана, 6 требований, 4 критерия приёмки»);
* если линковал epic или Confluence — упомяни.

Не пересказывай тело задачи — оно теперь в Jira, пользователь сам откроет.

## Worked example

Пользователь пишет:

> заведи стори про внедрение opentelemetry, проблематика — нужно повысить
> наблюдаемость; план — описать ADR, выбрать бекенд (elastic / vm-storage /
> cassandra), провести демо, нарезать подэпик на месяц, согласовать с Head
> of DevOps; требования — масштабируемость, фильтрация метрик, независимость
> от бекенда, grpc, чёткие роли collector/agent, распределение метрик от
> приложений, процент покрытия, роль метрик в процессе дежурств.

Тогда `summary` = `Внедрить OpenTelemetry для повышения наблюдаемости`.
А `description`, отрендеренный по `templates/story.wiki`, выглядит так:

```
h1. Проблематика

Необходимо для повышения наблюдаемости внедрить OpenTelemetry.

h1. Предполагаемый план решения

* Описать в виде ADR реализацию решения по OTel collector / метрикам.
* Выбрать и обосновать бекенд как часть компоненты:
** Elastic
** VM-storage
** Cassandra (или иные)
* Провести демо внутри команды для презентации предполагаемого решения.
* Создать подэпик с задачами на ближайший месяц для достижения цели.
* Согласовать данные задачи с Head of DevOps.

h1. Требования

* Платформа должна быть масштабируема.
* Должна быть фильтрация метрик.
* Бекенд может изменяться со временем — мы не должны быть на это завязаны.
* gRPC как протокол взаимодействия.
* Чётко определены роли OTel collector / agent.
* Распределение метрик, которые приносят приложения.
* Чётко описан процент покрытия метрик.
* Есть чёткая роль данных метрик и алертов в рамках процесса дежурств.

h1. Критерии приёмки (Acceptance Criteria)

* ADR опубликован в Confluence и принят командой.
* Выбран и зафиксирован бекенд хранения метрик с обоснованием.
* Подэпик создан, задачи нарезаны на ближайший месяц, оценены.
* Демо проведено, протокол с решениями приложен к задаче.
* План согласован с Head of DevOps (подпись в комментарии задачи).

h2. Definition of Done

* Все подзадачи закрыты.
* Метрики из MVP пишутся через OTel collector и видны в выбранном бекенде.
* Дежурные используют новые метрики в своих ритуалах (зафиксировано в runbook).

h1. Связанные документы и ссылки

* [Квартальный план|<URL из confluence_get_bookmark('quarterly_plan')>]
* [ADR (черновик)|<заполнить после публикации>]
```

Поля для вызова `jira_create_issue` в этом примере:

```
project    = "OPS"  (из defaults.yaml)
issue_type = "Story"
summary    = "Внедрить OpenTelemetry для повышения наблюдаемости"
labels     = ["from-claude", "planning", "current_sprint", "sprint-2026-w24", "theme-observability", "otel"]
priority   = "Medium"
description = <текст выше>
```

## Чего НЕ делать

* Не выдумывать пункты плана и требования, которых пользователь не сказал.
  Лучше попросить дополнить, чем сочинить.
* Не создавать задачу в проекте, не упомянутом в `defaults.yaml`
  / сообщении пользователя.
* Не использовать markdown (`#`, `**`, `-`) в теле задачи — только Jira wiki
  markup (`h1.`, `*bold*`, `*` для списков).
* Не дублировать создание: если в чате уже создавалась эта задача
  (есть `key` в истории) — предложить обновить через `jira_update_issue`,
  а не создавать новую.
* Не вписывать в описание секретов, паролей, токенов, доменов, которые
  попадают под маски из `redaction` в `config.yaml`.
