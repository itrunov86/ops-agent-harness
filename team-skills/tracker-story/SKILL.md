# Плановая задача в трекере

Скилл заводит задачи планового характера (внедрение, миграция, исследование, ADR) по одному шаблону, чтобы любую
инициативу команда видела в одинаковой форме и могла её обсудить и принять.

Файлы скилла:

* [`templates/story.wiki`](./templates/story.wiki) — структура описания;
* [`defaults.yaml`](./defaults.yaml) — проект, тип, метки, реестр тем, параметры спринта, пороги качества.

Шаблон и дефолты в рантайме не меняются: правка — обычным изменением репозитория.

## Когда применять

* «заведи стори про внедрение трассировки»;
* «создай задачу про миграцию метрик в новое хранилище»;
* «оформи задачу на выбор бэкенда для логов».

Не применять:

* для багов и инцидентов — у них свой тип и шаблон;
* для мелких операционных задач («выдай доступ», «подними виртуалку»);
* для эпика с подзадачами — [`tracker-epic`](../tracker-epic/SKILL.md).

Сомневаешься — спроси, подходит ли шаблон.

## Настройка под команду

В `defaults.yaml`:

* `tracker.project_key`, `issue_type`, `default_assignee` — по умолчанию `{{TRACKER_PROJECT}}`,
  `{{TRACKER_ISSUE_TYPE}}`, `{{TRACKER_ASSIGNEE}}`. Если в проекте нет типа Story — укажи доступный (часто `Task`);
* `tracker.labels` — постоянные метки задач из скилла (по ним удобно фильтровать);
* `tracker.theme_label_prefix` и `tracker.themes` — метка темы, настраивается: реестр направлений работы команды
  (мониторинг, CI/CD, безопасность…), по которому потом собирается статистика. Пустой реестр — скилл согласует
  тему с пользователем;
* `wiki.themes_page_url` — (необязательно) страница вики с таблицей тем, если реестр дублируется для людей;
* `wiki.related_link` — (необязательно) ссылка, которую всегда кладём в «Ссылки», например квартальный план;
* `sprint.reference_start`, `sprint.cadence_weeks` — якорь и длина спринта для метки спринта. Пусто — метку
  спринта не ставим;
* `tracker.epic_link_field` — поле связи с эпиком, если инстанс использует custom field (см. `tracker-epic`).

## Шаги

1. **Прочитай дефолты.** Если `project_key` пуст или пользователь его не подтверждал в этом разговоре — коротко
   спроси («создаю в проекте X, ок?»).
2. **Собери данные.** Если пользователь уже дал текст с блоками «проблема / план / требования» — бери его как есть,
   без добавлений. Не хватает — одно компактное сообщение с уточнениями, не серия вопросов.
3. **Проверь минимумы качества.** Меньше `behavior.min_plan_items` пунктов плана или
   `behavior.min_requirements` требований — попроси дополнить. Пустая задача никому не помогает.
4. **Подбери метку темы.** Ровно одна метка `<theme_label_prefix><тема>`:
   * сначала ищи подходящую тему в `tracker.themes`;
   * подходят несколько — один вопрос с 2–4 вариантами;
   * ни одна не подходит и направление действительно новое — согласуй короткое имя (kebab-case) с пользователем и
     предложи добавить тему в реестр (изменение репозитория; страницу тем в вики — только после отдельного
     подтверждения). Не плоди синонимы;
   * при `behavior.require_theme_label: true` не создавай задачу без метки темы.
5. **Посчитай метку спринта** (если заданы `sprint.*`):
   * `days = (today − reference_start).days` (отрицательно, если раньше якоря);
   * `sprint_start = reference_start + floor(days / (cadence_weeks × 7)) × cadence_weeks × 7 дней`;
   * метка — `sprint-{год sprint_start}-w{ISO-неделя sprint_start, две цифры}`;
   * плюс постоянная метка активного спринта из `tracker.labels`, если команда её использует.
6. **Заполни шаблон** [`templates/story.wiki`](./templates/story.wiki). Разметка — wiki markup трекера: `h1.`,
   `*`/`**` для списков, `[текст|url]`, inline-код — текст в двойных фигурных скобках, блоки —
   `{noformat}...{noformat}` или `{code:язык}...{code}`. Не markdown.
7. **Покажи черновик и получи подтверждение.** Summary, проект, тип, метки, первые ~10 строк описания, затем
   «создавать?». Без явного «да» задачу не создавай. Пропуск — только при `behavior.confirm_before_create: false`
   или постоянном разрешении в конфиге пользователя.
8. **Создай задачу** в трекере (например, `jira_create_issue`): проект, тип, summary (≤120 символов, без точки),
   описание, метки (постоянные + тема + спринт + названные пользователем), приоритет и исполнитель из дефолтов,
   если заданы. Без инструмента — отдай готовый текст и поля для ручного создания.
9. **По ситуации.** Пользователь назвал эпик (`{{TICKET_EXAMPLE}}`) и `behavior.link_to_epic_if_mentioned: true` —
   после создания свяжи задачу с эпиком (например, `jira_set_epic` или `jira_update_issue` с полем
   `tracker.epic_link_field`). Это отдельная запись — назови её в черновике шага 7.

## Ответ пользователю

3–5 строк: ключ и summary ссылкой (`{{TRACKER_URL}}/browse/<KEY>`), проект, тип, метки, одной строкой — что в
задаче («4 пункта плана, 5 требований, 3 критерия»), связь с эпиком, если ставил. Тело не пересказывай.

## Пример

Пользователь: «заведи стори про централизованный сбор логов: сейчас логи живут только на узлах и теряются при
пересоздании; план — сравнить два бэкенда, поднять стенд, описать ADR, договориться о хранении; требования —
хранение 14 дней, поиск по сервису, доступ по ролям».

* summary: `Внедрить централизованный сбор логов`;
* описание по шаблону: проблема — потеря логов при пересоздании узлов; план — 4 пункта; требования — 3 пункта;
  критерии — ADR принят командой, стенд собирает логи двух сервисов; ссылки — `(заполнить после ADR)`;
* метки: постоянные + `<prefix>logging` + метка текущего спринта.

## Чего не делать

* Не придумывать пункты плана и требования — лучше попросить дополнить.
* Не создавать задачу в проекте, которого нет в дефолтах или в словах пользователя.
* Не писать описание в markdown.
* Не дублировать: если задача уже создана в этом разговоре — предложи обновить её.
* Не вписывать секреты, токены, внутренние адреса и персональные данные.
